读完[快速开始](/docs/admin)并成功登录之后，本页带你完整开发第一个业务功能。案例是「岗位管理」，流程与任何真实业务资源一致：建表 → 后端实现 → 前端实现 → 菜单与按钮授权 → 页面验证。走完这一条线，你就能回答「在 ContiNew Admin 里加一个业务功能，从哪开始、到哪结束」。

每一步都给出验收点。建议先照做把岗位管理跑通，再开始做自己的功能；第一次定制就失败的话，很难分清是框架问题还是自己的改法问题。

框架的约定一句话概括：后端继承 CRUD 套件基类后，接口与权限码自动生成；前端目录即路由，菜单由后端按角色下发。机制细节见[CRUD 开发](/docs/admin/development/backend/crud)与[路由与页签](/docs/admin/development/frontend/route)。

## 第 1 步：建表

业务表遵循公共字段约定（`id`、`create_user`、`create_time`、`update_user`、`update_time`、`deleted`），实体继承 `BaseDO` 后这些字段自动填充。在目标库执行：

```sql
CREATE TABLE IF NOT EXISTS `sys_post` (
    `id`          bigint(20)   AUTO_INCREMENT              COMMENT 'ID',
    `name`        varchar(30)  NOT NULL                    COMMENT '名称',
    `description` varchar(200) DEFAULT NULL                COMMENT '描述',
    `sort`        int          NOT NULL DEFAULT 999        COMMENT '排序',
    `status`      tinyint(1)   UNSIGNED NOT NULL DEFAULT 1 COMMENT '状态（1：启用；2：禁用）',
    `create_user` bigint(20)   NOT NULL                    COMMENT '创建人',
    `create_time` datetime     NOT NULL                    COMMENT '创建时间',
    `update_user` bigint(20)   DEFAULT NULL                COMMENT '修改人',
    `update_time` datetime     DEFAULT NULL                COMMENT '修改时间',
    `tenant_id`   bigint(20)   NOT NULL DEFAULT 0          COMMENT '租户ID',
    `deleted`     bigint(20)   NOT NULL DEFAULT 0          COMMENT '是否已删除（0：否；id：是）',
    PRIMARY KEY (`id`),
    UNIQUE INDEX `uk_name_tenant_id_deleted` (`name`, `tenant_id`, `deleted`),
    INDEX `idx_create_user`(`create_user`),
    INDEX `idx_update_user`(`update_user`),
    INDEX `idx_tenant_id` (`tenant_id`),
    INDEX `idx_deleted` (`deleted`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='岗位表';
```

字段注释会成为响应对象的接口文档描述，认真写。写完把建表语句纳入 Liquibase 变更管理：在 `continew-server/src/main/resources/db/changelog/mysql/` 下新建 changeset 文件（如 `biz_post.sql`），并在 `db.changelog-master.yaml` 登记。仓库约定数据库结构变更同时提供 MySQL 与 PostgreSQL 两套 SQL，PostgreSQL 版本写到 `db/changelog/postgresql/`（写法对照同目录既有脚本）。**只新增 changeset，不要修改存量 changeset**——Liquibase 按 checksum 校验已执行的记录，改动会导致启动失败。`db.changelog-master.yaml` 默认启用 MySQL includes；选择 PostgreSQL 部署时按[部署](/docs/admin/reference/deployment#切换到-postgresql)的步骤切换 includes。

<Callout type="warn">
表名带 `tenant_id` 列即纳入行级租户隔离（继承 `TenantBaseDO` 的实体自动带出）。不需要租户隔离的公共表，要把表名加入 `continew-starter.tenant.ignore-tables` 白名单，机制见[多租户接入](/docs/admin/development/backend/tenant)。
</Callout>

## 第 2 步：后端实现

后端代码放 `continew-system` 模块的 `top.continew.admin.system` 包下（业务域不同就选对应模块），按分层子包落位：`model/entity`、`model/query`、`model/req`、`model/resp`、`mapper`、`service`（含 `impl`）、`controller`。完整形态可对照公告模块（`NoticeController`、`NoticeDO`、`NoticeServiceImpl` 等），下面按产出顺序走一遍。

新增的 Java 文件要带 Apache-2.0 License Header，类注释含 `@author`（署名使用者本人）与 `@since`（取 `5.0.0`），这些由 Spotless 与 Checkstyle 门禁强制，规范见根目录 AGENTS.md。

<Steps>
<Step>

写实体。`model/entity/PostDO.java` 继承 common 的 `BaseDO`，类上标 `@Data` 与 `@TableName(value = "sys_post", autoResultMap = true)`。JSON 列字段要同时加 `@TableField(typeHandler = JacksonTypeHandler.class)`——`autoResultMap` 漏了会导致该字段读出来恒为 null。写法对照 `NoticeDO` 的 `noticeUsers` 字段。

</Step>
<Step>

写查询、请求与响应三个模型。

- `model/query/PostQuery.java`：只放可筛选字段，实现 `Serializable`，`@Schema` 注解补接口文档（对照 `NoticeQuery`）；
- `model/req/PostReq.java`：校验注解齐全（`@NotBlank`、`@NotNull`、`@Length` 等），长度约束与建表 DDL 一致（对照 `NoticeReq`）；
- `model/resp/PostResp.java` 与 `PostDetailResp.java`：Resp 继承 common 的 `BaseResp` 放列表字段，DetailResp 继承 Resp 补详情字段（对照 `NoticeResp` 与 `NoticeDetailResp`）。

</Step>
<Step>

写 Mapper。`mapper/PostMapper.java` 继承 starter 的 `BaseMapper<PostDO>` 即可满足单表 CRUD；有联表或自定义查询时再声明方法，并在 `continew-system/src/main/resources/mapper/PostMapper.xml` 同步写 XML（对照 `NoticeMapper` 的 `selectNoticePage`）。接口声明了方法而 XML 缺失时，运行期才会报字段找不到。

</Step>
<Step>

写 Service。接口 `service/PostService.java` 继承 `BaseService<PostResp, PostDetailResp, PostQuery, PostReq>`；实现类 `service/impl/PostServiceImpl.java` 继承 `BaseServiceImpl<PostMapper, PostDO, PostResp, PostDetailResp, PostQuery, PostReq>`，类上加 `@Service` 与 `@RequiredArgsConstructor`，日志统一用 `@Slf4j`（对照 `NoticeService` 与 `NoticeServiceImpl`）。`BaseServiceImpl` 已内置 Crane4j 数据填充，响应对象上的填充注解开箱即用。

</Step>
<Step>

写控制器。继承 `BaseController<S, L, D, Q, C>` 五个泛型依次是 Service、列表响应、详情响应、查询条件、请求参数，类上标注 `@CrudRequestMapping`。

```java
@Tag(name = "岗位管理 API")
@RestController
@CrudRequestMapping(value = "/system/post",
    api = {Api.PAGE, Api.GET, Api.CREATE, Api.UPDATE, Api.BATCH_DELETE})
public class PostController extends BaseController<PostService, PostResp, PostDetailResp, PostQuery, PostReq> {
}
```

只写空类体：CRUD 接口由基类按 `api` 声明自动生成，权限码按路径推导（`POST /system/post` 要求 `system:post:create`），不要手写鉴权注解。资源特有的接口再在同一个控制器里追加，见[CRUD 开发](/docs/admin/development/backend/crud)的自定义接口一节。

写完执行 `./mvnw compile` 快速确认编译通过（完整门禁 `./mvnw verify` 放到最后统一跑）。

</Step>
</Steps>

## 第 3 步：前端实现

前端页面在 `continew-ui/src/routes/(main)/(app)/system/post/` 下开发。TanStack 文件路由约定「目录即 URL」：目录 `system/post` 对应路由 `/system/post`，`src/routeTree.gen.ts` 由 `pnpm dev` / `pnpm build` 自动生成，**不要手改**。

<Steps>
<Step>

封装 API。新建 `continew-ui/src/lib/api/post.ts`：从 `@/lib/http` 导入 `http`，导出 `PostResp`、`PostDetailResp`、`PostPageQuery`、`PostReq` 四个类型与 `listPosts`、`getPost`、`createPost`、`updatePost`、`deletePosts` 五个函数，写法对照 `notice.ts`（`deletePosts` 走 `http.del`，`body` 传 `{ ids: [...] }`）。不要绕过封装直接 `fetch`。

</Step>
<Step>

写页面组件。对照 `system/notice` 的既有形态建同级 `-components/` 目录：

- `route.tsx`：`createFileRoute('/(main)/(app)/system/post')({ component: PostList })`，组件从 `-components/` 导入；
- `-components/post-columns.tsx`：TanStack Table 列定义；
- `-components/post-list.tsx`：列表页，用 `useListTable` 管理分页与筛选，`DataTable` 出表格；
- `-components/post-form-drawer.tsx`、`post-delete-dialog.tsx`：新增/编辑抽屉与删除确认。

组件只用 `src/components/ui`（shadcn/ui）与 `src/components` 的现成业务组件，图标用 `lucide-react`，不引第二套 UI 库；表格列、筛选行、删除确认优先复用现有业务组件，不要从头写。

</Step>
</Steps>

## 第 4 步：菜单与按钮授权

<Steps>
<Step>

登录后在「系统管理 → 菜单管理」录入菜单：目录（类型 1）与页面菜单（类型 2），页面菜单的 `path` 填前端路由 URL（如 `/system/post`），规则见[菜单管理](/docs/admin/manual/system/menu)。按钮菜单（类型 3）的 `permission` 填后端推导出的权限码（`system:post:create`、`system:post:update`、`system:post:delete` 等），要与权限码推导规则逐字一致。

</Step>
<Step>

菜单或角色调整未即时生效时，点菜单管理页的「清除缓存」（`DELETE /system/menu/cache`）。

</Step>
<Step>

在「角色管理 → 修改权限」把新菜单授给目标角色，刷新页面即可看到入口。动态路由由后端按角色过滤下发，前端不做二次拦截。

</Step>
</Steps>

## 第 5 步：验证

进入「岗位管理」页面，依次验证：

1. 列表能打开（分页接口 `GET /system/post` 通，权限码 `system:post:list` 已生效）；
2. 新增一条岗位并能在列表看到（`POST /system/post`，`system:post:create`）；
3. 用一个未授权该菜单的测试账号登录，确认看不到入口、直调接口返回无权限。

到这一步功能就算完整落地了。之后再把包名、模块名、品牌元素改成你自己的项目信息；改完跑一遍 `./mvnw verify`（后端静态门禁与单元测试）与 `cd continew-ui && pnpm check`（前端格式、lint、类型、测试与构建）确认没有被定制破坏。

## 常见卡点

| 症状 | 原因与处理 |
|:-----|:-----------|
| 菜单配了，页面白屏 | 菜单 `path` 与 `routes` 目录对应的 URL 不一致，对照[路由与页签](/docs/admin/development/frontend/route)的映射规则修正 |
| 接口全部 403 | 按钮权限码与后端推导不一致，见[CRUD 开发](/docs/admin/development/backend/crud)的权限码生成规则 |
| 启动报 Liquibase checksum 不匹配 | 改了存量 changeset 而不是新增 |
| JSON 列字段读出恒为 null | 实体 `@TableName` 漏了 `autoResultMap = true` |
| PostgreSQL 环境建表失败 | 只写了 `db/changelog/mysql/` 一份 SQL |
| 前端构建类型报错 | `pnpm typecheck` 定位；对照仓库同版本页面修，不要用 `@ts-ignore` 绕过 |
