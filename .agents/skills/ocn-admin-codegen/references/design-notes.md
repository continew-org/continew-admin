# 设计取舍：从 4.2.x 旧脚手架生成器到本技能

本技能取代 4.2.x 的旧版脚手架生成器（Freemarker 模板 + `gen_config`/`gen_field_config` 两张配置表 + 独立插件模块）。
演进本技能前先读本文，避免把已经否决的旧形态又加回来。行文与产物请继续避开已退役功能的字面量
（PR #318 验收 grep 口径：中文与英文均已声明零命中，技能名中的 codegen 不受限）。

## 旧形态的弊端 → 本技能的对策

| 旧形态 | 弊端 | 本技能对策 | 落点 |
|:--|:--|:--|:--|
| Freemarker 模板固化分层写法 | 模板是约定的一次性快照，框架演进即静默漂移——4.x→5.x Query 改为 implements Serializable、前端整体换成 React/TanStack，旧模板产出的就是错模式的代码 | 生成时实读当前代码（SKILL.md §2 先读再写），import 与注解照抄仓库现状，不凭记忆不背规范 | SKILL.md §2 |
| 独立插件模块（31 文件）+ 2 张配置表 + 6 个菜单 | 不产生业务价值时的常驻维护面：启动即加载、发版即回归、界面本身还要占菜单与权限 | 零运行时：技能只是指令 + 样例，随仓库演进随 PR 更新，用户侧无任何常驻物 | 本技能形态 |
| 生成配置存数据库 | 配置不入版本控制；表结构变更后配置静默过期；必须先起应用、登录、走 UI 往返 | 决策落在会话问答与产物 diff 里，可审查、可版本化、可追溯 | SKILL.md §3 |
| 一次性渲染后复制粘贴落位 | 只产出代码文件；`query-keys.ts`、`master.yaml`、菜单 SQL、租户白名单等集成点全留手工，漏一步就是白屏、403 或启动失败 | 全链路一次补齐（P2-P4 各清单含集成点），交付前自验证双端构建 | SKILL.md §5、references/sql-and-menu.md |
| 配置对话框枚举受限（QueryType/FormType 固定项） | 表达不了枚举之外的意图：SpEL 校验、新插件模块、树形列表、主子表都要等模板升级 | 自然语言收集意图 + 结构化选择题确认；选项外的诉求走自由输入，当场采纳 | SKILL.md §3 |
| 只能从既有表起步 | 真正难的「从业务到表设计」完全留给用户，工具帮不上最前面一段 | 双入口并重：业务引导建表（含 DDL 确认门）与既有表解析 | SKILL.md §3、references/table-design.md |
| 交付即结束 | 「加导出」「改树形」要重走一遍配置流程，上下文全丢 | 产物是工作区里可迭代的 diff：追加诉求直接继续编辑，约定与上下文延续 | SKILL.md §5 P6 |
| 生成后无验证（旧文档止步于"放入对应项目"） | 编译错误、权限码不一致、路由不匹配全靠用户自己撞见 | P5 自验证：`./mvnw verify` + `pnpm fmt && build && check` + 实跑清单 + 交付 grep，不过不交付 | references/verification.md |

## 旧形态做对了、本技能必须保住的

- **完整性**：一次产出全套可跑文件，不让用户拼图 → P2-P4 各参考文档首节即产出清单，逐项打勾交付
- **字段级决策**：旧配置 UI 可逐字段设查询/表单 → 本技能改为「推荐映射表 + 用户只调例外」（SKILL.md §3 字段映射轮），
  既保留决策权又不用逐字段问
- **标准列模板**：旧文档 sys_post 示例的五审计列 + 租户列 + 索引写法 → 固化为 references/table-design.md 的建表规范
- **权限码与菜单一致**：按钮 permission 逐字等于 preHandle 推导值 → references/sql-and-menu.md 硬约束
- **诚实边界**：旧文档直言「细节仍需参考已有页面自行调整」→ P6 交付说明同样明示：脚手架完整且编译通过，
  CRUD 之外的业务逻辑仍需人工设计

## 写给执行本技能的智能体

- 不要退化成模板思维：用户的表再不标准，也先按仓库当前真实约定校准再动手，而不是照用户输入硬套
- 不要替用户做产品决策：范围与位置问清楚（SKILL.md §3）；字段映射给足默认但尊重调整
- 不要交付不可验证的承诺：能跑构建就跑构建，跑不了就明说缺什么环境，不把失败说成环境问题
- 后续演进走 diff 迭代，不推倒重造；发现本技能某条规则与仓库现状冲突，以仓库现状为准并回头修技能
